# HeyMelody feature and UI resource map

Investigation date: 2026-10-12. Scope: read-only packaged resources of `/Applications/HeyMelody.app/Wrapper/HeyMelody.app`. No app launch, earbud connection, device command, server request, or firmware operation was performed. Native code and REA/Ghidra conclusions are documented separately by the main investigation.

The user has selected **OnePlus Buds 4**. Its exact record and target-specific expected UI are documented in [oneplus-buds-4.md](oneplus-buds-4.md), with [RES-010 raw evidence](evidence/oneplus-buds-4-profile.json). This broader inventory includes other models' capabilities; generic localization must not be mistaken for Buds 4 feature eligibility.

## Newer AI live translation module

Observed copy includes conversation and simultaneous interpretation tabs, separate source/target language selection, mic start/listening state, connection and wearing prerequisites, autoplay on phone, generated-by attribution, bilingual vs translation-only view, portrait/landscape and face-to-face display. History supports item selection, copy/share/delete, and saving sessions. Permission copy in Info.plist describes microphone access for AI live translation. Sources: RES-002 keys `melody_hey_translation_*`; RES-003 `NSMicrophoneUsageDescription`.

The bundled copy advertises 100 free minutes per month, resets at midnight on the first of the month, under-five-minute warning, purchase time packs, remaining time and purchase history. Payment strings include App Store availability, iOS-version requirements, product lookup, token mismatch, verification failures and pending orders. Terms copy mentions country-specific customer support and exclusivity to HeyMelody rather than OPPO/OnePlus phone apps. These are static policy text, not evidence that the entitlement applies to this user or region, or that a web client can reuse the service. No service was contacted.

An inferred flow is: eligible connected/worn earbuds → microphone/consent/account gates → choose conversation or simultaneous interpretation → select languages → start mic session → recognized/translated transcript and optional speech playback → stop/save → history; quota depletion leads to checkout/history/settings. This is a product-flow hypothesis from strings, not an observed navigation graph. No translation NIB/storyboard is bundled in the inspected 54/13 resources, so layout, language availability per mode, routing, cloud provider, authentication, audio format and earbud control path remain unknown.

## Newer neck health module

The bundled configuration turns neck health on for some hidden model entries. That is not confirmed eligibility for OnePlus Buds 4, and it is not proof that a capability or server update cannot enable it on another model.

RES-002 has calibration guidance, posture monitoring, pressure/fatigue reminders, mobility assessment and history, exercise videos, angle results, symmetry results, failure/retry and interruption states. The data disclosure string `melody_ui_data_collect_health_illustrate` explicitly describes an IMU (gyroscope + accelerometer), six neck-angle directions, posture durations and calibration time. Poor-posture reminders mention 10–20 consecutive minutes, prompt tone and phone notification. Bundled webp/JSON assets correspond to preparation and six directions, but asset names alone are not proof of runtime sequence.

An inferred flow is: eligible connected/worn earbuds → introduction/permission → fit instruction and head-still calibration → calibration result/retry → enable monitoring and tone/notification reminders → mobility test following video → six directional angle results, rotation/lateral-flexion symmetry → history/reassessment → exercise library. Copy disagrees on assessment duration (`neck_health_activity_subtitle`: three-minute video; `melody_health_mobility_intro_subtitle`: one minute/seven exercises). Preserve this discrepancy until active code determines which text is used. The app's own static disclaimer says assessments do not substitute for clinical diagnosis; no health algorithm or clinical accuracy was validated.

## Device configuration structure

The fallback whitelist reports `newVersionCode="2.30.0"` and `versionCode=1.01`. Each record combines identity (`id`, name/brand/alias/internal mark/type), connection candidates (`uuid`, `ctkd`, `gattV2`, `minRiss`, `checkResponse`), app gating (`newMinVersion`), firmware category and feature configuration. Top-level `additionInfo` is empty. Nested `headsetAdditional` and function `additional` are retained even when empty.

There are 23 `isHidden=true`, 2 explicit false and 34 absent hidden flags. Model types are T1 (38), T2 (18), N (3); their semantics need native code. `gattV2=1` appears on 50 entries and is absent on 9; `ctkd=1` on 54 and absent on 5. The UUID field is `0000079A-D102-11E1-9B23-00025B00A5A5` on 58 and `00001107-D102-11E1-9B23-00025B00A5A5` on one. These resource UUIDs do not establish whether they are advertised service UUIDs, a pairing identifier, or the transport actually selected. See protocol findings for corroboration.

`function.control` arrays contain raw gesture IDs, per-ear fields, supported function numbers, human descriptions and optional localization-key overrides; `button=6` marks call-control descriptions in several records. `equalizerInfo.types` carries preset IDs and localization keys, with optional firmware/app minimums. `switchStatus` arrays enumerate numeric candidates; resources do not name the feature behind each number. `mutexFunctions` encodes explicit pairwise conflict names. Tutorial arrays/intro entries carry IDs, icon/localization keys and optional minimum app version. Build the eventual compatibility resolver from these structures plus actual device responses and version checks, rather than a generic all-features-enabled UI.

## Resource-level unknowns and next evidence

1. Target model is now OnePlus Buds 4 (`065414`). Firmware version and host/browser platform remain unknown. Full multi-model parity requires separate profiles.
2. Dynamic visibility: trace whitelist decode, server override, model-ID match, runtime feature responses, firmware constraints, region/account gates and numerical enum decoding in native code.
3. UI fidelity: passive app observations are needed for real screenshots, connected vs disconnected pages, page order, defaults, dynamic code-built views, translation and health interfaces.
4. Hearing/health computations: recover algorithm inputs/outputs, storage schema, filtering/calibration, test/result safety states and whether calculation happens on device, host or service.
5. Cloud-backed resources/services: identify endpoint families and request/response schemas offline first; licensing, authentication, entitlement and regional availability remain unresolved without explicitly authorized live access.
6. Asset catalog content is opaque in this inventory. Extract existing raster/vector identities only if needed for visual fidelity, without treating logos/media as automatically reusable licensed assets.
7. Model availability must distinguish bundled fallback, hidden flag, app-accepted IDs, physical-device capability response and actual retail support.
8. Do not implement firmware update, sound transfer, log extraction or noisy locate/test commands until packet transaction semantics and relevant model constraints are validated; this resource pass does not authorize or perform device writes.
